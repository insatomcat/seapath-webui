Running, and not declared

Pacemaker runs these and the inventory describes none of them. A convergence will not touch them, and a guest added under one of these names would collide with what is already there.

Resource Node Role State

A guest is an entry of the VMs group in the inventory, naming its disk image and its libvirt XML. The image goes in the artefacts, which git does not carry, and the XML is committed with the inventory: both are uploaded from the Inventory page, and a run mounts them under the same root, so the path the entry writes resolves either way. Deploying them is a run of the playbook named above, from the Deployment page.

{# The one form on this page. It asks for what a guest is made of and nothing else: a name, a disk image, and the libvirt XML that describes it. Everything the roles can read off an entry beyond that is edited in the file, on the Inventory page, where a site's own variables live. #}

Add a VM

The image and the XML are uploaded, the guest is written into the inventory as a commit, and the deployment playbook is run. Existing guests are left alone by that run.

It becomes the libvirt domain name and the Pacemaker resource, so it is what every other tool will call this VM.

{# Shown where the inventory has machines of both kinds. The guest goes into `cluster_VMs` or `standalone_VMs`, and everything below follows from it: the playbook that creates it, the options its entry may carry, and whether it has an RBD image at all. #}

A cluster guest is created by deploy_vms_cluster, its disk lives in the Ceph pool and Pacemaker places it. A standalone one is created by deploy_vms_standalone, its disk is a file in the local libvirt pool, and libvirt alone runs it.

The image a creation starts from, stored outside git. In a cluster it is imported into the Ceph pool and the guest runs from there afterwards.

Committed with the inventory. A file ending in .j2 is taken as a Jinja2 template and rendered per guest, anything else is used as it is.

Placement, migration and real time

A pinned guest runs on that node or stays down. A preferred one starts there when it can and moves when it cannot.

Which guests Pacemaker keeps running when it cannot run them all. Higher wins.

The user the migration runs as is livemigration_user, which is one value for the whole cluster and lives in the inventory beside the other cluster variables.

The system disk of a cluster guest is not in the XML you bring: vm_manager builds that element itself, because it has to name the RBD image, the Ceph monitors and the libvirt secret. This is the one knob on the element it builds.

Read by the seapath-alloc hook at every start and every migration. What deploy_seapath_alloc documents, and an alternative to a fixed cpuset in the XML.
